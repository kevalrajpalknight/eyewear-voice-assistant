EVA Eyewear Assistantlocal-first voice agent for smart glasses

A voice assistant that lives in your glasses and thinks on your own hardware

EVA listens through a wake phrase, answers in a natural voice, looks through the glasses camera, searches the web and checks the weather. Most of the thinking runs on a CPU-only PC. The cloud model is called only when a request really needs it.

What it is

The glasses (an AIMB-G2 unit) have a camera, microphones, speakers and a Bluetooth link. The vendor app works only with its own cloud. This project talks to the glasses directly: it decodes their Bluetooth protocol, streams the wearer's voice, takes photos, and plugs the result into an AI agent built with LangChain.

Everything is designed to be extended: new abilities are added as tools, and the same code can later sit behind a phone and a server.

Why it is built this way

Local first

Privacy, cost and speed. Pictures never leave the PC. Simple questions never touch the cloud.

Safe by construction

Only approved Bluetooth commands can be sent. Anything that could update, erase or reset the glasses is blocked in code.

Measured, not guessed

Every claim on these pages comes from a run on the real machine. Where something was not measured, it says so.

Small, auditable code

Eight packages, one place for the AI framework, ADRs for each major decision, a test that guards the boundaries.

Models and measurements

Hardware: a Windows PC, 8 logical cores, 12 GB RAM, no GPU. Free memory during development was often only 2 to 5 GB, which shaped most choices.

Local model speed by thread count

Seconds to the first token of a ~300-token prompt, with two other CPU-heavy processes running (like speech recognition and synthesis would be). More threads did not help.

Generation speed stayed at 9 to 11.5 tokens per second for every setting: decoding is limited by memory bandwidth, not by cores.

Tool choice accuracy (16 test requests)

Test: a real local model, fake tools, requests such as "do I need an umbrella in Mumbai" or "look at this packet and tell me if it is healthy". A case counts as correct only when the right tools, and no others, were called.

Features and what can be stacked next

Working today

Voice

  • Always listening with a wake phrase, sleeps after 3 s of quiet
  • Speak over it to interrupt
  • Ignores its own echo, background sounds and "um"
  • Natural voice with pauses between sentences

Agent

  • Instant rules for time, date, camera, weather, thanks
  • Local model for everything else
  • Cloud model for research and when the local one fails
  • Narrates each step ("Let me look…") and says when it is still working

Tools

  • Look through the camera and describe it (local vision)
  • Web search with a Wikipedia fallback
  • Weather, time, battery, photo count, take a photo
  • Multi-step plans: look, then search, then answer

Engineering

  • Per-stage timing in every turn log, colour-coded by who answered
  • Offline diagnose that traces a phrase without sending anything
  • Config check, pinned dependencies, ADRs
  • Write guard with a hard "never send" list

Honest limits

  • The glasses send a 384 by 288 picture by default, so small print is hard to read. A larger size is one approved setting away and still to be tested.
  • A 2 billion parameter model is weak at deciding when to use tools. The fix (forced tool plans from word cues) is reliable for the cases it covers, not for open-ended requests.
  • Always-on listening uses the PC microphone. The glasses' own microphone only streams after a button press or the firmware wake phrase.
  • Latency for tool turns (10 to 19 s) is long. Narration covers the wait; shortening it is the next piece of work.
All numbers come from runs on the development machine in October and November 2026. Source: the project repository, docs folder (ADRs, protocol notes, configuration).
